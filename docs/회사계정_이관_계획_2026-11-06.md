# LX Group MI 회사 계정 이관 계획 (2026-11-06)

현재 시스템은 개인 계정(n8n `sondullab`, 구글 `master@sondullab.com`, GitHub `utaxx`)에 걸쳐 있다. 이것을 회사 계정으로 옮기는 가장 간단한 방법을 정리했다. **아직 아무것도 옮기지 않았다.**

## 1. 결론

- **「옮기기」가 아니라 「회사 계정에 복제한 뒤 전환」으로 한다.** 개인 시스템은 전환이 끝날 때까지 그대로 돌린다. 문제가 생기면 대시보드 주소만 되돌리면 된다.
- **n8n 인스턴스를 통째로 넘기면 안 된다.** 같은 인스턴스에 개인 매매(AutoTrading), SondulNews, 무원406 워크플로우가 섞여 있다(전체 64개 중 LX는 43개). LX 워크플로우만 골라 내보낸다.
- **구글 파일은 소유권을 넘길 수 없다.** 구글은 다른 도메인으로 소유권 이전을 허용하지 않는다. 회사 계정에서 사본을 만들거나 다시 수집하면 파일 ID가 전부 바뀐다. 이것이 이관 작업량의 대부분이다.
- **사람이 직접 해야 하는 일은 계정 만들기와 로그인(인증)뿐이다.** 나머지(목록 작성, ID 바꾸기, 워크플로우 가져오기, 시험, 문서)는 내가 할 수 있다.
- **먼저 회사 보안 정책 세 가지를 확인해야 한다(§2).** 이 답에 따라 방법이 바뀐다.

|---|---|---|

## 4. 실수하기 쉬운 곳

1. **워크플로우 ID가 다른 워크플로우 안에 적혀 있다.** 오류 워크플로우 지정(`LXGroup_실패알림`), 하위 워크플로우 호출(수동실행 → 각 수집기, MI → MI_Sub, 수집저장 → 공시수집기·실적추출 등)이 ID로 연결돼 있다. 가져오면 ID가 새로 붙으므로 「옛 ID → 새 ID」 대응표로 다시 이어야 한다. 이것을 빠뜨리면 겉으로는 정상인데 호출만 실패한다.
2. **시트 안에 ID가 들어 있다.** 설정 시트의 「고객시트링크」, 경쟁사 시트의 「드라이브폴더」, 운영설정의 DART 파일 ID, 기사파일 시트의 파일 ID가 그렇다. 워크플로우만 바꾸고 시트 값을 안 바꾸면 옛 계정 파일을 계속 쓴다(옛 계정을 닫는 순간 멈춘다).
3. **OAuth 크리덴셜은 사람이 로그인해야 한다.** 내가 대신할 수 없다. 회사 구글 계정은 개인 메일이 아닌 **공용 계정**(예: 팀 공용 메일)으로 만들어야 담당자가 바뀌어도 시스템이 멈추지 않는다.
4. **파일은 개인 「내 드라이브」가 아니라 회사 「공유 드라이브」에 둔다.** 2026-10-30에 드라이브 루트의 공개 파일 3개가 지워져 기업 검색이 이틀 멈췄다. 공유 드라이브는 조직 소유라 한 사람의 정리 작업이나 퇴사로 파일이 사라지지 않는다.
5. **실행 기록과 시트 변경 이력은 넘어가지 않는다.** 필요한 기록은 옮기기 전에 문서로 남긴다(HANDOVER.md에 대부분 있다).
6. **같은 시각에 두 시스템이 같은 외부 API를 부르면 한도를 나눠 쓴다.** 병행 기간에는 회사 쪽 예약 실행을 개인 쪽과 다른 시각으로 둔다. DART 일일 한도(키별 2만 건)는 키가 다르면 따로다.

## 5. 진행 순서

### 0단계 — 지금 개인 시스템에서 미리 할 일(내가 한다, 반나절)
- `hub.html`의 n8n 주소 29곳을 `N8N_BASE` 상수 하나로 모으고, 드라이브 파일 ID·구글 API 키·시트 링크도 맨 위 설정 블록 하나로 모은다. 이관 때는 이 블록만 바꾼다.
- LX 워크플로우 43개를 내보내 저장소에 넣고(비밀값은 없다. 키는 시트에 있다), 각 워크플로우가 쓰는 시트·폴더·파일 ID와 다른 워크플로우 호출을 표로 뽑는다. 이 표가 「대응표」의 왼쪽이 된다.
- 쓰지 않는 임시 워크플로우(TMP_·임시_ 5개)는 옮기지 않는다.

### 1단계 — 회사 계정 준비(사용자, 1~3일, 대부분 기다림)
1. 회사 구글 공용 계정과 공유 드라이브 1개(예: 「LX MI」).
2. 회사 n8n(Cloud 가입 또는 사내 설치)과 그 n8n의 API 키. 회사 n8n을 Claude Code에 MCP로 연결한다.
3. Anthropic Console에서 회사 조직·결제 등록 후 API 키 발급.
4. 회사 GitHub 조직(또는 사내 저장소)과 Claude GitHub 앱 설치.
5. API 키 재발급: DART, ECOS, KOSIS, FRED, 관세청(data.go.kr). 텔레그램을 계속 쓸 경우 회사용 봇.

### 2단계 — 데이터 옮기기(나와 사용자, 반나절)
- 사용자: 개인 계정에서 설정 스프레드시트 등 원본 시트를 회사 공용 계정에 공유한다(보기 권한이면 충분하다).
- 나: 회사 계정 쪽에서 사본을 만들어 공유 드라이브에 넣고, 새 ID를 대응표 오른쪽에 채운다. 「운영설정」의 키 값은 비워 두고 사용자가 회사 키를 직접 넣는다(키는 대화로 받지 않는다).
- 원문 XML 폴더는 복사하지 않는다. 경쟁사 시트의 「드라이브폴더」 값을 비우면 회사 쪽 공시수집기가 폴더를 새로 만들고, 원문저장이 다시 받아 채운다.

### 3단계 — 워크플로우 옮기기(나, 1일)
- 내보낸 JSON에서 대응표로 시트·폴더 ID를 바꾸고, 크리덴셜 연결을 회사 크리덴셜로 바꿔 가져온다.
- 가져온 뒤 새 워크플로우 ID로 하위 호출과 오류 워크플로우 지정을 다시 잇는다.
- 사용자가 크리덴셜 4개(Sheets, Drive, Gmail, Telegram)에 회사 계정으로 로그인한다.
- 워크플로우마다 draft 수동 실행으로 확인한 뒤 게시한다(CLAUDE.md 규칙 그대로). 키가 들어가는 워크플로우의 실행 데이터 저장 끔 설정도 그대로 옮긴다.

### 4단계 — 대시보드 옮기기(나, 반나절)
- 회사 저장소로 옮기고 `hub.html` 설정 블록의 값만 바꾼다.
- 회사 정책에 따라 GitHub Pages, 사내 호스팅, Apps Script 웹 앱 중 하나로 띄운다.

### 5단계 — 병행 운영과 전환(1~2주)
- 두 시스템을 같이 돌리며 같은 날 같은 화면의 숫자(지표, 경쟁사 실적, 기사 수)를 비교한다.
- 맞으면 사용자에게 새 대시보드 주소를 안내하고, 개인 쪽 LX 워크플로우를 비활성화한다(삭제는 한 달 뒤).
- 개인 쪽 공개 JSON 파일과 공개 저장소의 회사 관련 내용 정리 여부를 정한다.

## 7. 다른 선택지

- **A안(권장): 위 순서대로 회사 n8n + 회사 구글 + 회사 GitHub.** 지금 구조를 거의 그대로 쓰므로 위험이 가장 작다.
- **B안: 회사 Google Workspace 안에서 끝내기(n8n 없이).** 수집·조회를 Apps Script로 옮기고 대시보드도 Apps Script 웹 앱으로 띄운다. 외부 SaaS가 없고 접근을 회사 로그인으로 막을 수 있다. 다만 2026-09-07 설계(`docs/앱스스크립트_이관_설계_2026-09-07.md`)는 기반 코드만 있고, 43개 워크플로우를 다시 만들어야 하므로 A안보다 몇 배 오래 걸린다. 회사가 외부 SaaS를 막을 때만 고려한다.
- **C안: 개인 n8n을 그대로 두고 회사 계정만 연결.** 가장 빠르지만 실행 주체와 결제가 개인으로 남아 「회사 시스템」이 되지 않는다. 임시로만 쓸 수 있다.

5. 알림 수단(텔레그램 회사 봇 / 회사 메일).
