# 문서 문체 정리 (2026-10-19)

저장소 문서에 남아 있던 어색한 표현을 일반적인 한국어 실무 문체로 고쳤다. 이 문서는 무엇을 왜 어떻게 바꿨는지, 무엇을 일부러 남겼는지를 적는다. 바꾼 문장 전체는 `docs/문체_정리_변경목록_2026-10-19.md`에 있다.

## 1. 배경

- `CLAUDE.md`의 글쓰기 규칙은 `README.md`·`hub.html`·`manual.html`·`docs/`에서 금지어를 모두 정리했다고 적고 있었다(2026-09-06). 실제로는 `docs/HANDOVER.md`와 `README.md`에 순우리말 조어와 어색한 표현이 많이 남아 있었다.

## 2. 고친 기준

**고친 것 (산문만)**

- `CLAUDE.md` 표의 금지어와 같은 계통: 칸·줄 → 컬럼·행·셀·영역, 단추 → 버튼, 자료 → 데이터, 갈래 → 종류·구분, 열쇠 → 키, 낱말 → 키워드·단어 등
- 부르다 → 호출하다, 돌려주다 → 반환하다, 뽑다 → 추출하다, 걸러내다 → 필터링하다, 손으로 → 수동으로, 판(版) → 버전, 시간표 → 스케줄, 까닭 → 이유·원인
- 우리말 수 표기 → 숫자: 스물여섯 → 26, 열두 달 → 12개월, 석 달치 → 3개월치, 이레 → 7일, 넉 장 → 4개
- 비유·잠언조 문장을 설명체로: "~것보다 낫다", "빨갛게 끝난다"(→ 실패한다), "머리카락 굵기입니다"(→ 거의 보이지 않을 만큼 얇습니다) 등
- 1인칭 표현("내가 만든 오류" 등)과 의미가 불분명한 신조어

**바꾸지 않은 것**

- 코드 블록, 인라인 코드, 「」로 감싼 UI 라벨·노드 이름·시트·컬럼·워크플로 이름
- 한글 함수·변수 이름(`설정보이기()`, `판올리기()`, `칸()` 등), 웹훅 질의 파라미터 `갈래`
- 파일명·경로·URL, 날짜·숫자·ID·버전 표기, 사실관계와 결론

## 3. 방법

1. 문서를 6개 구간(HANDOVER 4구간, README, 나머지 문서 4개)으로 나눠 검토자 6명이 각각 「원문 → 수정문 → 이유」 목록만 만들었다. 검토자는 문서를 직접 고치지 않았다.
2. 목록을 사본에 적용하면서 자동 검사를 했다.
   - 원문이 문서에서 정확히 한 번만 나오는지, 다른 항목과 겹치지 않는지
   - 코드 블록·인라인 코드·「」 이름·URL이 바뀌지 않았는지(바뀌면 그 항목은 제외)
   - 숫자가 줄어들지 않았는지(늘어난 숫자는 우리말 수 표기를 숫자로 바꾼 것인지 전부 확인)
3. 표본을 직접 읽어 의미가 바뀌지 않았는지 확인했다. 무작위 60건, 부정어 수가 달라진 72건, 길이가 크게 바뀐 항목, 숫자가 늘어난 항목 전체를 봤다.
4. 1차에서 놓친 어휘(머리줄, 표시줄, 선택 줄, 까닭, 열두 달, 손으로 등)는 2차로 직접 고쳤다.

### 9-2. 고치지 않은 것

- 코드 토큰(문자열 리터럴, 변수·함수 이름, 정규식 포함), 노드 이름, 연결, 시트·컬럼 이름, 웹훅 질의 파라미터 `갈래`
- 응답 메시지, 시트에 적는 안내 문구, 마커(「부문표 못 찾음」 등) 같은 코드 안 문자열. 바꾸면 동작이 달라진다.
- 노드 `notes`: 수정 도구가 없다.
- 노드 이름(「손으로 부를 때」, 「요약 손익 되줍기」, 「읽을 보고서 고르기」, 「부문 거르기」 등)과 코드 변수 이름(`열쉰`, `갈래실적` 등). 바꾸면 `$('노드이름')` 참조가 깨진다.

### 9-3. 방법과 검증

1. 워크플로 6묶음을 담당자가 나눠 맡았다. 담당자는 코드 노드마다 수정 전후 코드를 파일로 저장하고, 토큰(주석 제외)이 같은지와 문법을 `acorn`으로 검사한 뒤에만 draft에 저장했다. 발행과 실행은 하지 않았다.
2. 첫 단계 검사는 파일만 보고 n8n에 실제로 저장된 값은 보지 못했다. 그래서 전송 단계에서 글자가 틀리는 사고가 있었다. 한 묶음에서 `$('한 탭씩')`이 `$('한 탭씨')`로 바뀌었고, 코드가 중간에서 잘려 저장된 적이 있었으며, 문자열 속에 오타가 섞인 적이 있었다. 모두 담당자가 찾아 고쳤다.
3. 그래서 발행 전에 **n8n의 수정 전 버전과 현재 draft를 `get_workflow_versions_diff`로 비교**하는 독립 검증을 했다. `__old`/`__new`의 jsCode 토큰이 같아야 통과로 봤다. 정규식 리터럴 비교 약점은 검증 전에 고쳤다. 검증 결과 앞의 사고는 모두 이미 복구돼 있었고, 새로 발견된 오류는 없었다.
4. 통과한 28개만 발행했다.

### 9-4. 확인하지 못한 것과 주의

- **CLAUDE.md의 「publish 전에 draft를 수동 실행해 확인」은 하지 않았다.** 주석만 바꿨고 토큰 동일성을 검증했으며, 대부분이 PW나 외부 호출이 있어 안전하게 실행할 수 없기 때문이다. 발행 뒤 첫 정기 실행과 화면 조회를 확인해야 한다.
- 「경쟁사_원문저장」, 「경쟁사_공시수집」은 검증 중 안전 분류기가 담당자의 파일 쓰기를 중단시켜 검증하지 못했다(DART 키를 다루는 코드로 보인다). 두 워크플로는 draft만 바뀌었고 활성 버전은 그대로다. 검증은 다른 방법으로 나중에 해야 한다.
- 원문에 글자가 깨진 주석이 있었다(「곇 차례」, 「짎다」, 「끩어졌다」, 「퓈도」, 「둘렇다」, 「첫 당을 값을」 등). 담당자가 문맥으로 풀어 썼다. 뜻이 틀렸을 수 있다. 해당 노드: 「경쟁사_부문매핑마스터」의 부문 모으기·보탤 줄 만들기, 「경쟁사_비용추출」의 비용 뽑기, 「경쟁사_마스터정리」의 회사마다 표 짜기, 「경쟁사_공시수집」의 주소 만들기·새 공시만 고르기, 「경쟁사_원문저장」의 받을 것 고르기. 특히 「경쟁사_공시수집」의 「첫 당을 값을 → 첫 번째로 채워진 값을」은 코드 동작과 맞는지 확인이 필요하다.
- 코드 안 문자열에 오타가 남아 있다: 「경잃사 시트에…」(「경쟁사 시트에」), 「뜽니다」(`부문매핑마스터` 안내 문구), 「볼만한표」(`비용추출`).
- 설명과 실제가 어긋난 곳: 「경쟁사_부문매핑마스터」 안내 문구는 「여섯 시간마다」인데 실제 스케줄은 주 1회(금 06:10), 「라벨관리」 설명은 동작 3개인데 코드는 5개, 「캘린더소스관리」 설명은 동작 3개인데 코드는 `rename`까지 지원한다.
- 「무원406 대시보드 자료」의 「맞는 열쇠 찾기」 노드 코드에 접속 키로 보이는 고정 문자열이 있다. 담당자는 값을 출력하지 않았고 수정하지도 않았다. 이 저장소가 공개라는 점에서 n8n 코드가 아니라 시트·자격 증명으로 옮기는 것을 권한다.
- 「LXGroup_지표수집」의 「지표 고르기」 노드는 `throw new Error`를 쓴다. 메시지에는 키 이름만 들어가지만 CLAUDE.md 안전 규칙(「Code 노드에서 throw 하지 않는다」)과 어긋날 수 있다.
- 「LXGroup_딜공시수집」은 활성 버전이 매일 08:00, draft가 주 1회 금 08:30이다. 어느 쪽이 의도한 것인지 정한 뒤 발행해야 한다.

### 9-5. 되돌리기

각 워크플로의 수정 전 버전으로 `restore_workflow_version`을 쓰면 된다. 수정 전 버전 ID는 이 작업의 작업 파일(세션 임시 폴더)에만 있고 저장소에는 없다. n8n의 워크플로 이력(`get_workflow_history`)에서 「주석 문체 정리」 이전 버전을 찾으면 된다.
