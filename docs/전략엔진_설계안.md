# 전략 엔진 고도화 — 현 구조 분석 및 마이그레이션 설계안

인수인계서(Ensemble Score 기반 모듈형 전략 엔진)를 현 코드베이스에 적용하기 위한
분석·설계 문서. **구현 전에 합의할 내용**을 정리한 것이며, 아직 코드는 바꾸지 않았다.

---

## 1. 현 구조 분석

### 1.1 전체 흐름

```
유니버스(시총 상위 18~60)          settings(DB, 암호화·이력)
        │                                  │
        ▼                                  ▼
  KIS/Yahoo 일봉 ──▶ Strategy ──▶ RiskManager ──▶ OrderExecutor ──▶ 알림/DB
                   (종목 1개씩)   (거부만 함)      (시장가 전량)
```

- `TradingEngine`(실거래)과 `BacktestEngine`(백테스트)이 **같은 순서**로 짜여 있다.
  이건 이미 잘 되어 있는 부분이고, 앞으로도 유지해야 한다.
- 전략 21종은 `registry.py`에 등록되고, 활성 전략 키 하나를 DB 설정으로 고른다.
- 리스크 정책·인증정보·텔레그램은 전부 DB(`app_settings`)에 있고 변경 이력이
  자동으로 남는다. 대시보드에서 재시작 없이 바꿀 수 있다.

### 1.2 결정적 제약 — `Strategy` 인터페이스가 종목 하나만 본다

```python
class Strategy(ABC):
    def generate_signals(self, symbol: str, price_history: pd.DataFrame) -> list[Signal]
```

이 시그니처에는 **다른 종목도, 지수도, 날짜별 순위도 들어올 수 없다.** 따라서
인수인계서의 핵심 Factor 중 두 개가 지금 구조에서는 원리적으로 구현 불가능하다.

| Factor | 필요한 것 | 현 인터페이스로 가능? |
|---|---|---|
| Relative Strength | 같은 날 전 종목의 수익률 분포(횡단면 순위) | ❌ |
| Market Regime | 지수 가격·이동평균, 유니버스 전체의 Breadth | ❌ |
| Trend / Momentum / Pullback / Breakout / Volume / Volatility | 해당 종목 시계열만 | ✅ |

**→ 인터페이스 변경이 이 작업의 최우선 선결 과제다.** 이걸 먼저 정리하지 않으면
RS·Regime을 넣으려다 전략 코드 곳곳에 전역 상태를 주입하는 형태가 되어, 문서가
경계하는 "복잡한 조건문을 계속 덧붙이는" 구조로 간다.

### 1.3 발견된 실제 결함 — 전략이 포트폴리오 상태를 들고 있다

`VolumeSurgeStrategy`(현재 활성 전략 `volume_surge_5d`)는 `generate_signals` 안에서
`entry_index` 변수로 "지금 보유 중"을 스스로 기억한다.

실제로 돌려서 확인한 결과:

```
급등일 2번(3일 간격)을 준 데이터 → 매수 신호는 1번만 발생
  2025-01-22 buy   거래량 2배 급증 + 10.0% 상승
  2025-01-27 sell  보유 5일 경과 청산
```

문제는 이 "보유 중"이 **엔진의 실제 보유와 아무 관계가 없다**는 점이다.

- 리스크 매니저가 매수를 거부했거나(동시보유 8종목 초과, 일일 손실 한도),
  현금이 부족해 엔진이 안 샀어도 → 전략은 샀다고 믿고 이후 신호를 막는다.
- 며칠 뒤 내는 매도 신호는 있지도 않은 포지션을 향한 것이라 엔진이 무시한다.

즉 **자리가 없어서 한 번 못 산 종목은, 그 뒤 며칠간 기회가 와도 신호 자체가
안 나온다.** 종목 수를 60개로 늘려 자리 경쟁이 생기면 이 결함의 영향이 커진다.

인수인계서 39항 "전략 로직과 주문 로직을 섞지 않는다"에 정확히 해당한다.
보유 여부 판단은 엔진(포트폴리오)이 갖고, 전략은 "지금 이 종목이 매력적인가"만
답해야 한다.

## 2. 목표 구조와의 차이(Gap)

| 인수인계서 요구 | 현재 | 난이도 |
|---|---|---|
| Factor별 Score | 조건식 True/False | 중 |
| Weight / Enabled / 자동 재정규화 | 없음 | 하 |
| Threshold를 Config에서 | RiskPolicy만 DB, 전략 파라미터는 코드 | 중 |
| Market Regime 상위 Layer | 없음 | **상** (지수·Breadth 데이터) |
| Relative Strength | 없음 | **상** (인터페이스 변경) |
| ATR Stop / Trailing / Take Profit | 고정 % 손절만 | 중 |
| Risk 기반 Position Sizing | 고정 비중 | 중 |
| 섹터 노출 한도 | 섹터 데이터 없음 | **불가(현재)** |
| Fundamental Factor | 데이터 소스 없음 | 보류 |
| 수급(외국인·기관) Factor | 데이터 소스 미확인 | 보류 |
| CAGR/Sharpe/Sortino/PF/Expectancy | 수익률·MDD·승률·거래수만 | 하 |
| Factor Contribution 분석 | 없음 | 하 (Enabled 토글이 생기면 자동) |
| 판단 근거 로그(Explainability) | 사유 문자열 1줄 | 하 |
| Slippage | 미반영 (수수료·세금만) | 하 |
| Look-ahead 방지 | ✅ 이미 처리 | — |
| Walk Forward | ✅ `robustness.py`로 구간별 검증 중 | — |

### 2.1 데이터로 막히는 것 — 솔직히 적는다

- **Fundamental / 수급**: 지금 쓰는 데이터 소스(KIS 일봉, Yahoo)에 없다. KIS에
  투자자별 매매동향 API가 있으나 모의투자 지원 여부를 확인하지 않았다.
  인터페이스만 열어 두고 Phase 7로 미루는 게 맞다.
- **섹터**: 종목별 업종 코드를 안 받아오고 있다. `max_sector_exposure`는
  업종 데이터를 먼저 확보해야 한다.
- **유니버스 60종목 상한**: KIS 순위 API가 시장당 30개까지만 준다(직접 확인).
  RS 백분위를 60개 안에서 매기면 해상도가 거칠다. 늘리려면 연속조회 구현 필요.
- **생존 편향(Survivorship Bias)**: 지금 유니버스는 **오늘 시점** 시총 상위로
  뽑는데, 그걸로 과거를 백테스트하고 있다. 즉 인수인계서 26항이 경계하는
  생존 편향이 **이미 기존 검증 결과에 들어 있다.** 과거 시점의 구성종목을
  KIS에서 받을 방법이 없어 당장 해결이 어렵다 — 최소한 결과에 명시해야 한다.

## 3. 목표 구조 매핑

### 3.1 새 인터페이스 — 유니버스 전체를 보는 전략

기존 `Strategy`를 **없애지 않고** 상위 개념을 추가한다.

```python
@dataclass(frozen=True)
class MarketContext:
    """어느 하루의 판단에 필요한 모든 것. 미래 데이터는 들어가지 않는다."""
    as_of: date
    histories: dict[str, pd.DataFrame]   # 종목별, as_of까지만 잘라서
    index_history: pd.DataFrame | None   # 지수(시장 국면용)
    held: set[str]                       # 지금 보유 중인 종목 — 전략은 읽기만


@dataclass(frozen=True)
class Evaluation:
    """한 종목에 대한 평가 결과 — 점수와 '왜'가 함께 다닌다."""
    symbol: str
    total_score: float
    factor_scores: dict[str, float]
    decision: str          # NO_TRADE / WATCH / BUY / STRONG_BUY
    reasons: list[str]


class PortfolioStrategy(ABC):
    def evaluate(self, ctx: MarketContext) -> list[Evaluation]: ...
```

기존 21종은 어댑터로 감싸 같은 경로에 태운다.

```python
class SingleSymbolAdapter(PortfolioStrategy):
    """기존 Strategy 하나를 유니버스 전체 평가로 변환. 매수 신호=100점,
    없으면 0점. 기존 전략을 대조군으로 계속 쓰기 위한 다리."""
```

이렇게 하면 **대시보드·전략 리뷰·다기간 검증·리포트가 전부 그대로 동작**한다.
새 엔진은 registry에 전략 하나(`factor_score_v1`)로 추가되어, 기존 21종과 같은
자리에서 비교된다. 이게 이 프로젝트에서 가장 위험이 적은 이식 경로다.

### 3.2 디렉터리

인수인계서 32항 구조를 현 패키지에 맞춰 배치한다.

```
src/muwon/
  factors/            (신규)
    base.py           Factor 인터페이스 + 정규화 도우미
    trend.py  momentum.py  pullback.py  breakout.py
    relative_strength.py   volume.py    volatility.py
    (fundamental.py  flow.py — Phase 7)
  market/             (신규)
    regime.py         국면 판정 + 국면별 파라미터
  scoring/            (신규)
    engine.py         Weight 적용·재정규화·임계값 판정
    config.py         FactorConfig / StrategyConfig 스키마
  risk/               (기존 확장)
    manager.py        기존 유지
    sizing.py         (신규) ATR 기반 수량 계산
    exits.py          (신규) ATR 손절/트레일링/이익실현
  backtest/
    metrics.py        (신규) CAGR·Sharpe·Sortino·PF·Expectancy
```

`factors/new_factor.py`를 추가하고 config에 한 줄 넣으면 끝나는 구조를 목표로 한다.
Score Engine은 Factor 목록을 순회할 뿐 개별 Factor를 알지 못한다.

### 3.3 Factor 공통 인터페이스

```python
class Factor(ABC):
    key: str                       # config에서 참조할 이름

    def score(self, symbol: str, ctx: MarketContext) -> FactorResult:
        """0~100으로 정규화된 점수와 근거 문장을 돌려준다.
        데이터가 모자라면 None을 돌려 '평가 불가'로 처리하고,
        그 Factor의 가중치는 재정규화에서 빠진다."""
```

> **정규화 규칙을 처음부터 못 박아 둔다: 모든 Factor는 0~100.** 지금 엔진에 넣은
> `Signal.score`는 전략마다 척도가 다른데(거래량 배수, 돌파 폭 %), 그건 "한 번에
> 한 전략만 돈다"는 전제 위에서만 성립한다. 여러 Factor를 더하는 순간 척도가
> 통일돼 있지 않으면 가중치가 아무 의미도 갖지 못한다.

### 3.4 설정 스키마

```json
{
  "buy_threshold": 75,
  "strong_buy_threshold": 85,
  "factors": {
    "market_regime":     {"enabled": true,  "weight": 15, "params": {}},
    "trend":             {"enabled": true,  "weight": 15, "params": {"mas": [20,60,120,200]}},
    "momentum":          {"enabled": true,  "weight": 20, "params": {"periods": [5,20,60,120]}},
    "relative_strength": {"enabled": true,  "weight": 20, "params": {"benchmark": "^KS11"}},
    "pullback":          {"enabled": true,  "weight": 20, "params": {"rsi_period": 5, "rsi_max": 35}},
    "volume":            {"enabled": true,  "weight": 10, "params": {"ma_window": 20}},
    "breakout":          {"enabled": false, "weight": 10, "params": {"period": 55}},
    "fundamental":       {"enabled": false, "weight": 10, "params": {}},
    "flow":              {"enabled": false, "weight": 10, "params": {}}
  },
  "exits": {
    "atr_stop":      {"enabled": true, "multiple": 2.0},
    "trailing_stop": {"enabled": true, "multiple": 3.0},
    "trend_exit":    {"enabled": true},
    "score_exit":    {"enabled": true, "threshold": 50},
    "take_profit":   {"enabled": false, "steps": [[2, 0.33], [4, 0.33]]}
  },
  "sizing": {"risk_per_trade_pct": 0.5, "max_position_pct": 15, "max_exposure_pct": 80}
}
```

- `enabled=false`인 Factor는 합계에서 빠지고 **나머지 가중치를 100 기준으로 자동
  재정규화**한다(인수인계서 5항).
- 데이터가 없어 평가 불가인 Factor도 같은 방식으로 빠진다. 이게 없으면 수급
  데이터가 하루 안 들어온 날 전 종목 점수가 통째로 내려앉는다.

### 3.5 국면별 파라미터 override

```json
{
  "regimes": {
    "STRONG_BULL": {"buy_threshold": 70, "max_exposure_pct": 100},
    "BULL":        {"buy_threshold": 75, "max_exposure_pct": 80},
    "NEUTRAL":     {"buy_threshold": 80, "max_exposure_pct": 50},
    "BEAR":        {"buy_threshold": 90, "max_exposure_pct": 20}
  }
}
```

**Breadth는 우리 유니버스 60종목으로 계산한다.** 별도 데이터 소스가 필요 없고
(이미 60종목 일봉을 다 받아온다), 지수 데이터가 막혀도 국면 판정이 돌아간다.
지수(`^KS11`)는 백테스트에서 Yahoo로 확보 가능하고, 실거래에서는 KIS 업종지수
조회가 필요하다 — **미확인이므로 Breadth 단독으로도 작동하게 설계한다.**

## 4. 단계별 Migration Plan

각 단계는 **기존 21전략이 계속 동작한 채로** 끝나야 한다.

### Phase 1 — 경계 정리 (기능 변화 없음)

1. `MarketContext` / `Evaluation` / `PortfolioStrategy` 정의
2. `SingleSymbolAdapter`로 기존 21종을 새 경로에 태움
3. 두 엔진(실거래/백테스트)이 `PortfolioStrategy`만 호출하도록 변경
4. **`VolumeSurgeStrategy`의 보유 상태를 엔진으로 이관** (§1.3 결함 수정)

> 이 단계의 성공 기준: **21전략의 백테스트 결과가 이전과 100% 동일**할 것.
> (단 `volume_surge_5d`는 결함 수정으로 결과가 달라진다 — 그 차이를 별도 보고)

### Phase 2 — Config 골격

5. `StrategyConfig` 스키마 + DB 저장(JSON) + 기본값
6. Weight 재정규화 로직 + 임계값 판정

## 7. 이 설계에서 지키는 원칙

인수인계서 39항을 이 프로젝트 문맥으로 옮기면 다음과 같다.

1. Factor는 0~100으로 정규화한다 — 안 그러면 Weight가 의미를 잃는다

6. 각 Phase는 기존 기능을 깨지 않고 끝난다
7. 새 전략이 기존 21종보다 낫다는 것은 **백테스트로 확인한 뒤** 말한다

## 9. BEAR 이중 적용 조사 (2026-08-18)

### 발견 ① BEAR는 '기준이 높다'가 아니라 '매수 불가'다

국면 Factor는 두 곳에서 동시에 작용한다 — 총점을 끌어내리고(BEAR 20점),
매수 문턱도 올린다(BEAR 90). 방향이 같아 효과가 겹친다.

```
국면          국면점수  국면기여  천장   문턱   나머지 Factor에 요구되는 %
STRONG_BULL     100     15.0   100.0    70          64.7%
BULL             75     11.2    96.2    75          75.0%
NEUTRAL          50      7.5    92.5    80          85.3%
BEAR             20      3.0    88.0    90         102.4%  ← 불가능
```

문제는 차단 자체가 아니라 **설정의 90이 거짓말**이라는 점이다. 85로 낮춰도
아무것도 안 바뀐다. `threshold_reachability()`가 이를 계산해 경고한다.

### 발견 ② STRONG_BUY가 그 문턱을 뚫는 통로였다 (수정함)

판정 사다리는 위에서부터 검사한다. `strong_buy_threshold`(85)가 국면
문턱(90)보다 낮으므로, 85~88점은 BUY 검사에 닿기도 전에 STRONG_BUY로
통과한다. 약세장 문턱이 무력화되고, 그렇게 산 종목에 'STRONG_BUY'라는
이름표까지 붙어 로그가 사람을 속인다.

관문을 `max(strong_buy_threshold, 국면 문턱)`로 바꿨다. **다만 이 우회로가
실제로 열린 적은 없다** — 2022년 BEAR 구간 최고 점수가 18종목 81.7,
58종목 81.5로 둘 다 85에 못 미쳤다. 예방적 수정이지 손실의 원인이 아니다.

### 발견 ③ 2022년 손실의 원인은 BEAR가 아니다

58종목 · 2022년 · **-39.12%** (MDD -41.16%, 50거래)

```
■ 국면별 문턱과 실제 도달 점수
  STRONG_BULL  문턱 70  천장 100.0  실제최고 90.4   STRONG_BUY=7 BUY=132
  BULL         문턱 75  천장  96.2  실제최고 89.1   STRONG_BUY=9 BUY=170
  NEUTRAL      문턱 80  천장  92.5  실제최고 87.3   STRONG_BUY=5 BUY=14
  BEAR         문턱 90  천장  88.0  실제최고 81.5   (매수 0건)  ← 도달 불가

■ 진입 시점 국면별 손익
  BULL          30건  승 1  -2,690,900원
  NEUTRAL       10건  승 0    -693,106원
  STRONG_BULL   10건  승 0    -520,819원
```

**BEAR 121일(전체의 50%) 동안 매수는 0건.** 차단은 완벽히 작동했다.
손실은 전부 BULL·NEUTRAL·STRONG_BULL로 판정된 날의 진입에서 났고,
50건 중 49건이 손실이다(승률 2%). BULL 하나가 손실의 69%를 만들었다.

국면 전환 시점을 보면 원인이 드러난다.

```
2022-01-04 시작 → BULL      2022-05-04 NEUTRAL → BULL
2022-04-04 BEAR → BULL      2022-08-22 NEUTRAL → BULL
                            2022-11-25 BEAR → STRONG_BULL
```

전부 하락장 중간의 단기 반등 구간이다. 그리고 강세로 판정되는 순간 매수
문턱이 70~75로 **가장 느슨해진다** — 가장 위험한 자리에서 가장 헐겁게 산다.

### 왜 이렇게 되는가

Breadth는 **수준(level) 지표**다. '20일선 위 종목 비율'은 가격이 이미 오른
뒤에야 올라가므로, 반등 꼭지에서 최고값을 낸다. 평활화·확정지연은 전환
횟수를 67→19회로 줄였지만 **방향은 고치지 못했다.** 잡음만 제거됐고 남은
것은 진짜 신호처럼 보이는 오판이다.

손절은 정상 작동했다(상위 손실 5건 전부 [손절], 평균 보유 16일). 고칠 곳은
청산이 아니라 **진입 허용 판정**이다.

### 다음 가설

하락 추세 안의 반등과 추세 전환을 구분하려면 수준 외에 **방향**이 필요하다.
유니버스 동일가중 지수를 만들어 그 지수가 자기 장기 이동평균 위에 있을
때만 BULL/STRONG_BULL을 허용한다(고전적 시장 필터). 2022년 KOSPI는 연중
내내 200일선 아래였으므로, 이 조건이면 그 해의 BULL 선언이 전부 막힌다.

검증 전까지 기본값으로 켜지 않는다 — ATR 손절도 그럴듯했지만 실측에서
기각됐다.

## 10. 시장 필터 — 두 번의 기각과 한 번의 채택 (2026-08-18)

### 1차 가설: 지수가 자기 장기 평균선 위일 때만 강세 — **기각**

58종목 · 2022년 진단:

```
■ 시장 필터  상승추세 판정 152/529일 (29%)   설정 {"uptrend_ma": 200}
■ 국면 분포  STRONG_BULL 12 / BULL 36 / NEUTRAL 75 / BEAR 121
  (필터 없음) STRONG_BULL 14 / BULL 36 / NEUTRAL 73 / BEAR 121
■ 손익 -39.12% — 필터 없을 때와 완전히 동일
```

필터는 켜져 있었다(529일 중 152일만 통과). 그런데 확정 국면은 STRONG_BULL
2일이 옮겨간 것뿐이고 강세 선언 시점 14곳이 전부 그대로였다.

**이 판별은 계측을 붙였기에 가능했다.** 그 전에는 파라미터 0/60/120/200이
소수점까지 같은 결과를 내는 것만 보였고, "효과가 없었다"인지 "켜지지도
않았다"인지 구분할 수 없었다. `MarketRegimeFactor.uptrend_days`와
`diagnose_period --regime-params`가 그걸 갈랐다.

계측을 붙이는 과정에서 `diagnose_period`가 자기만의 예열값(200일)을 들고
있는 것도 드러났다. 200거래일 이동평균이 거의 안 채워져(상승추세 24/381일)
같은 설정인데 실험과 진단이 다른 답을 낼 수 있었다. **같은 뜻의 상수를 두
곳에 따로 두면 반드시 갈라진다.**

### 왜 기각됐는가

하락 추세에서도 반등이 크면 가격이 잠시 평균선을 넘는다. **그리고 그 자리가
정확히 반등 꼭지다.** 그러니 '평균선 위'는 잡으려던 바로 그 순간에 통과한다.

### 2차 가설: 평균선 자체가 오르고 있을 때만 강세 — **채택**

평균선의 기울기를 함께 본다(`uptrend_slope`). 반등으로 가격이 평균선을
넘어도, 1년째 내려온 평균선은 아직 아래를 향한다.

58종목 · 2021~2025 (uptrend_ma=200 고정):

```
설정        2021    2022    2023    2024    2025     평균     최악    CAGR  Sharpe    MDD    PF   거래
slope=  0   +1.7   -39.1   +54.8   -10.7  +148.1   +31.0   -39.1   +31.4   0.27  -41.2  0.80   189
slope= 20   +1.7   -32.7   +97.6   -10.7  +148.1   +40.8   -32.7   +41.5   0.41  -35.0  1.04   176
slope= 60   +1.7   -29.2   +97.6   -10.7  +148.1   +41.5   -29.2   +42.2   0.42  -32.4  1.03   169
slope=120   +0.3   -29.1   +96.5    -1.8  +125.0   +38.2   -29.1   +38.8   0.39  -31.8  1.23   144
```

slope=60에서 **모든 지표가 동시에 좋아진다** — 최악 -39.1 → -29.2,
평균 +31.0 → +41.5, Sharpe 0.27 → 0.42, PF 0.80 → 1.03, MDD -41.2 → -32.4,
거래 189 → 169건.

`uptrend_ma=200, uptrend_slope=60`을 기본값으로 켰다.

### 이 결과를 읽을 때의 단서

1. **평균 수익률에 대한 효과는 유니버스를 탄다.** 18종목에서는 같은 설정이
   평균을 +14.2 → +9.9로 **떨어뜨렸다**(2023년 +61.6 → +38.3). 반면 **최악
   구간은 두 유니버스 모두에서 개선됐다**(-8.7 → -7.3 / -39.1 → -29.2).
   그래서 이건 '수익을 늘리는 장치'가 아니라 **'최악 구간을 줄이는 장치'**로
   이해해야 하고, 이 시스템의 1순위 판단 기준이 최악 구간이라 채택했다.
2. 네 값 중 가장 좋은 것을 골랐다. 값 하나를 유니버스 하나에서 고른 것이라
   과최적화 위험이 남아 있다.
3. 절대 수익률은 여전히 생존 편향이 실려 있다(§8). 상대 비교만 읽어야 한다.
4. **실거래 전략은 바꾸지 않는다.** 최악 -29.2%는 여전히 실계좌에 올릴
   수준이 아니다. 같은 조건의 volume_surge_5d는 다섯 해 전부 플러스(최악
   +13.0%)다.

### 덤으로 막은 것

`StrategyConfig.from_json`이 `params`를 통째로 갈아 끼우고 있었다. params
없이 저장된 설정 하나가 시장 필터를 조용히 꺼 버릴 수 있었다 — 문서가
"빠진 키는 기본값을 쓴다"고 약속한 것과도 어긋났다. 기본값 위에 얹도록
고치고 테스트로 못 박았다.

## 11. 자금을 갈래로 나눌 것인가 (2026-08-18)

제안: 자금의 일부(예: 30%)를 공격적 단기 스윙 갈래로 떼어, 별도 전략·별도
손절/익절로 운영한다.

### 전제 확인 ① 전략들이 서로 다른 때에 움직이는가 — **그렇다**

### 결론 — 지금은 만들지 않는다

갈래 구조는 설정 스키마·리스크 매니저·백테스트/실행 엔진·유니버스 빌더를
전부 건드리는 작업이다. 그 비용을 치를 근거가 아직 없다.

**다만 이 실험은 제안의 절반만 검증했다.** '다른 전략'은 확인했지만
**'다른 종목군'은 확인하지 못했다.** 위 역추세 전략들은 전부 시가총액 상위
58종목 위에서 돌았다. 제안의 핵심은 거래량 상위 종목군이었고, 그건 지금
유니버스 빌더가 시가총액 순위만 지원해서 테스트할 방법이 없다.

### 다음에 확인할 것

1. KIS 거래량/거래대금 순위 API로 별도 유니버스를 만든다
2. **그 종목군에서** 단기 전략이 돈이 되는지 본다 — 여기서 지면 갈래를
   만들어도 작은 상자 안에서 잃을 뿐이다
3. 이기면 그때 갈래 구조를 만든다

### 자금 단위 문제 (구조를 만들 때 반드시 다뤄야 함)

1,000만원의 30%는 300만원이다. 그 갈래가 4종목을 들면 종목당 75만원인데,
고가주(삼성바이오로직스 ~100만원)는 1주도 못 산다. 목표 비중과 실제 비중이
어긋나면 백테스트와 실거래가 따로 논다. 공격적 갈래일수록 저가·중소형주
유니버스여야 이 문제가 줄어든다 — 거래량 상위가 마침 그쪽이라 방향은 맞다.

## 12. 거래대금 유니버스에서 다시 재기 (2026-08-18)

§11에서 남은 질문: 역추세·단기 전략이 시총 상위에서 진 것은 전략이 나빠서인가,
운동장이 틀려서인가.

KIS 거래량순위 API(FHPST01710000)로 거래대금 상위 30종목을 뽑았다. 시총
목록과 23종목이 다르다 — 금융지주·바이오 대형주가 빠지고 하나마이크론·
제주반도체·심텍·주성엔지니어링·HPSP 같은 중소형 변동성 종목이 들어왔다.

```

volume_surge_5d           +16.7    +8.2   +53.5   +17.4   +77.8   +34.7    +8.2   1.52  -17.2  1.43   797
factor_score_v1           +11.5   -13.1   +60.9   +26.3   +84.3   +34.0   -13.1   0.83  -25.2  1.09   124
volume_surge_3d           +23.1    +4.6   +28.5    +0.7   +33.5   +18.1    +0.7   1.34  -17.3  1.45   494
```

### 가설은 절반 맞았다

운동장을 바꾸니 역추세 전략의 **피해가 크게 줄었다**.

```

```

역추세 전략이 대형주에서 크게 깨진 것은 전략만의 문제가 아니었다.

### 그런데 결론은 바뀌지 않는다

덜 깨지게 됐을 뿐, **여전히 벌지 못한다.** rsi2_pullback은 5년 평균 연
+1.2%에 Sharpe 0.04다. 628번 매매해서 그 정도면 자본을 위험에 노출시킨
대가가 없는 것이다. bollinger_reversion도 평균 +8.4%에 최악 -12.2%로,
volume_surge_5d(평균 +34.7%, 최악 +8.2%)와 섞을 이유가 없다.

**volume_surge_5d가 두 유니버스 모두에서 1등이고, 두 곳 모두 5년 전부
플러스다.** 실거래 전략을 바꿀 이유가 없다.

거래대금 유니버스에서 5년 전부 플러스인 전략이 하나 더 있다 —
volume_surge_3d(최악 +0.7%, Sharpe 1.34). 다만 volume_surge_5d와 상관이
0.60으로 가장 높은 조합이라(§11) 분산 상대로는 최악이다. 같은 논리의
전략이므로 당연한 결과다.

### 최종 판단

자금을 갈래로 나누는 구조는 만들지 않는다. 두 조건 중 하나가 계속 미충족이다.

- 갈래끼리 상관이 낮을 것 → **충족** (0.13~0.60)
- 갈래 모두가 돈을 벌 것 → **미충족** (두 유니버스, 여섯 전략에서 확인)

거래대금 유니버스와 kind 분리는 남겨 둔다. 나중에 쓸 만한 단기 전략을
찾으면 그때 이 위에서 바로 잴 수 있다.

### 이 표를 읽을 때

30종목은 **오늘** 거래대금 상위다. 2021년부터 되돌려 돌리면 생존 편향이
시총 유니버스보다 **더 심하다** — 시총 상위는 5년 전에도 큰 회사였지만,
오늘 거래가 몰리는 종목은 그 사이 테마를 탄 종목이다. 절대 수익률은 더욱
믿을 수 없고, 전략 간 순위 비교만 유효하다.

종목 수도 다르다(58 vs 30). 유니버스 간 절대 비교가 아니라 '각 유니버스
안에서의 순위'로 읽어야 한다.

## 13. 슬리피지 — 종가 체결 가정이 결과를 얼마나 부풀렸나 (2026-08-18)

지금까지의 모든 숫자는 "종가에 원하는 만큼 체결됐다"는 가정 위에 있었다.
실제로는 호가가 벌어져 있고 시장가로 치면 반대 호가를 먹고 들어간다.
6만원짜리 종목의 호가 단위가 100원이라 한 칸이 0.17%다.

### 결론은 살아남았다

volume_surge_5d는 0.20%에서도 다섯 해 전부 플러스다(최악 +2.6%). '최악

### 그런데 크기는 못 믿는다

평균 +50.5% → +26.3%로 **거의 반이 사라진다.** Sharpe도 1.70 → 1.03이다.
앞으로 이 전략을 말할 때 '연 50%'는 쓰면 안 되는 숫자다. 여기에 생존
편향(§8)까지 얹히므로 절대 수익률은 더더욱 참고값일 뿐이다.

### 회전율이 전부다

factor_score_v1은 슬리피지를 0.20%까지 올려도 거의 안 변한다(평균 +41.5 →
+38.5). 5년에 169거래뿐이기 때문이다. volume_surge_5d는 1,259거래(연 250회)
라 같은 비용이 7배 넘게 붙는다.

**여기서 순위가 지표에 따라 갈린다.** 0.20%에서 평균 수익률만 보면
factor_score_v1(+38.5)이 volume_surge_5d(+26.3)보다 높다. 그러나 최악
구간은 -29.9% 대 +2.6%다. 1순위 기준이 최악 구간이므로 판단은 바뀌지
않지만, '어느 자로 재느냐'에 따라 답이 달라진다는 것은 기록해 둘 만하다.

### 18종목에서는 훨씬 약했다

같은 전략이 18종목에서는 0.05%에서 이미 '5년 전부 플러스'가 깨졌다
(최악 +0.9 → -1.4). 종목 수가 적으면 고를 후보가 적어 한계 거래가
나빠지기 때문으로 보인다 — 다만 확인한 것은 결과뿐이고 원인은 추정이다.

### 기본값은 0으로 둔다

바꾸는 순간 지금까지의 모든 결과와 비교가 안 되고, 얼마가 맞는지는
실거래 체결 기록으로만 알 수 있다. 모의투자 주문을 쌓아 실제 체결가와
종가의 차이를 재는 것이 다음 할 일이다 — 그때까지는 값을 고르지 않고
민감도로만 본다.

## 14. 운영 상태 점검 — "기록이 유실됐나, 애초에 안 샀나"

계측 도구를 하루 종일 만들었는데(슬리피지 실측, 알림 탭, 요약 카드) 전부
"매매 기록이 쌓인다"를 전제로 했다. 그 전제 자체가 확인된 적이 없었다.

### 처음 가설: 기록이 유실됐다 — 기각

paper-trading 워크플로 8회 중 유일한 자동(schedule) 실행이 구글드라이브
업로드 단계에서 `HttpError 403 ... storageQuotaExceeded`로 실패했다. 매매는
했는데 상태 DB를 못 올린 것이라면 기록이 사라진다.

운영 DB를 읽기 전용으로 받아 보니 아니었다.

| 테이블 | 건수 |
| --- | --- |
| 백테스트 | 73 |
| 유니버스 스냅샷 | 150 |
| 설정 | 13 |
| 주문·보유·완결매매 | 0 |

엔진 상태에 `cash = 10,000,000`이 정확히 초기값 그대로 남아 있었고, KIS
계좌 대조도 "현금 일치, 보유 0개"였다. 저장은 되고 있다. **산 적이 없는
것이다.**

### 왜 안 샀나

성공한 실행 로그가 그대로 답이었다.

```
저장된 유니버스 스냅샷이 없어 기본 목록을 사용합니다.
매매 대상 18종목
점검 종목 수: 18
체결 없음
```

활성 전략 `volume_surge_5d`는 "거래량이 5일 평균의 2배"를 찾는다. 그
조건이 시가총액 상위 18개 대형주에서 뜨는 일은 드물다. 같은 실행의 일일
리뷰에서도 이 전략은 3개월에 3거래였다.

**실험과 실거래가 다른 종목을 보고 있었다.** 모든 실험은 60종목으로 돌았고
(`시세 60종목`), 실거래는 기본 18종목으로 돌았다. 시총 스냅샷이 적용된 지금은
둘 다 60종목이다 — 다음 자동 실행부터 맞는다.

### 진짜 문제: 신호 0건이 아무 뜻도 없었다

`signals` 테이블은 스키마에만 있고 코드 어디에서도 쓰이지 않았다. 그래서
"신호 0건"이 **신호가 없었다**인지 **기록을 안 했다**인지 구분할 수
없었다. 대시보드도 같은 문제를 갖는다 — 빈 화면이 "오늘 살 게 없었다"와
"오늘 아예 안 돌았다"를 동시에 뜻한다. 둘은 고치는 방법이 정반대다.

그래서 두 가지를 넣었다.

- `signals` — 전략이 낸 신호를 실제로 남긴다
- `run_logs` — 회차마다 한 줄: 대상/판단 종목 수, 매수·매도 신호 수,
  주문 수, 리스크 매니저가 막은 이유, 현금·평가금액

체결이 없어도 남기고, 시세를 하나도 못 받아도 남긴다(그 경우 `run_date`가
NULL이라 그 자체가 "데이터 공급이 끊겼다"는 신호다). 이제 표 한 줄이면
갈린다 — 신호가 0이면 전략 문제, 신호는 있는데 주문이 0이면 막힌 이유가
같은 줄에 있다.

## 15. 청산 조건은 한자리에 모여 있어야 한다

"지금 매도 전략은 기간밖에 없어?"라는 질문을 받았다. 화면이 그렇게 읽히게
만든 것이 문제였다.

### 실제로 파는 조건은 셋이고, 엔진은 이 순서로 본다

`TradingEngine`/`BacktestEngine` 모두 보유 종목마다 아래를 차례로 검사하고,
**먼저 걸리는 것 하나**로 판다.

1. **손절** (`risk/exits.py evaluate_exit`) — 고정 -5%. `atr_stop_enabled`를
   켜면 ATR 배수로, `trailing_stop_enabled`를 켜면 고점 대비 트레일링이
   추가된다. 둘 다 지금은 꺼져 있다(2022년 검증에서 손실이 커져 기본값 끔).
2. **보유 기간** — 전략의 `max_holding_days`. 지표가 아니라 시간이다.
3. **전략 자신의 매도 신호** — `SignalType.SELL`.

지금 활성 전략 `volume_surge_5d`는 3번이 **없다**. `generate_signals`가 BUY만
낸다. 그래서 이 전략의 청산은 **손절 -5%와 5거래일 경과** 둘뿐이다.

### 익절이 없다

`take_profit`에 해당하는 것이 코드 어디에도 없다. 오르는 중이면 위 조건 중
하나에 걸릴 때까지 그대로 들고 간다. 의도한 설계가 아니라 **아직 안 만든
것**이다.

`volume_surge_5d`에서는 이게 특히 크게 작용한다. 파는 조건이 시간이라,
3일째 +15%가 나 있어도 5일째까지 기다렸다가 그날 종가로 판다. 그 사이 되돌림을
그대로 맞는다.

넣을지는 검증할 문제다. 익절을 너무 낮게 잡으면 크게 벌 기회를 스스로 자른다 —
추세추종 계열은 "몇 번 크게 먹는 것"으로 먹고 사는데 익절이 그걸 막는다.
`volume_surge_5d`가 5년 평균 +50%를 낸 것도 큰 이익 몇 번 덕일 수 있다.
**먼저 잴 것**: 지금 청산되는 매매들의 보유 기간별 손익 분포. 5일째에 파는
값이 3일째 고점보다 얼마나 낮은지를 봐야 익절선을 논할 수 있다.

### 화면을 고쳤다

파는 조건이 전략(보유 기간)·리스크 정책(손절)·엔진(순서) 셋에 흩어져 있는데,
화면에서까지 흩어 놨던 것이 오해의 원인이었다. 전략의 매도 신호만 "🔴 이럴 때
팝니다"에 있고 손절은 저 아래 "항상 적용되는 규칙"에 있었다.

`exit_rules(strategy, policy)`가 **엔진이 검사하는 순서 그대로** 셋을 합쳐
한자리에 낸다. 그리고 **없는 것도 적는다** — "익절은 없습니다", "ATR 손절은
꺼져 있습니다". 없는 걸 안 적으면 '있는데 안 보이는 것'과 구분이 안 된다.

## 16. 익절 — 재보고 기각

§15에서 "익절이 아예 없다"를 확인하고, 넣을지를 실제로 쟀다.

### 개별 매매로는 건질 것이 없다

운영 60종목 2021~2025, `volume_surge_5d` 완결 매매 **1,259건**의 보유 구간
종가 경로를 되짚었다(장중 고가는 쓰지 않는다 — 일봉 종가로 판단하고 다음 날
아침에 주문을 내므로 실제로 잡을 수 없는 값이다).

| 구분 | 건수 | 고점 중앙 | 청산 중앙 | 되돌림 중앙 |
| --- | ---: | ---: | ---: | ---: |
| 전체 | 1,259 | +2.49% | −0.25% | +3.25% |
| **이익 매매** | 599 | +7.02% | +5.08% | **+0.28%** |
| **손실 매매** | 660 | **+0.00%** | −5.22% | +5.79% |

두 줄이 전부다.

- **이긴 매매는 고점 근처에서 판다.** 되돌림 중앙값 +0.28% — 익절로 건질
  것이 없다.
- **진 매매는 애초에 오른 적이 없다.** 고점 중앙값 +0.00%(산 날이 고점).
  익절선이 몇이든 안 닿으므로 **익절은 손실 매매를 하나도 못 구한다.**

익절선 후보별 도달률도 같은 말을 한다. +15%에 닿은 111건(8.8%)의 실제 청산
중앙값은 **+19.67%**였다 — 그 선에서 팔았다면 꼬리를 자른 셈이다. 모든
후보에서 실제 청산이 그 선보다 높았다.

### 그런데 스윕은 다르게 나왔다 (60종목)

개별 매매에서 손해인데 계좌 전체로는 좋아지는 이유는 **자금 회전**이다.
익절로 일찍 팔면 현금이 생겨 다른 종목을 산다(거래 1259 → 1331). 잘린

다만 곡선이 매끄럽지 않다. +10%는 기준보다 **나쁘고**(+49.1 < +50.5)
+15%에서 튀었다가 +20%, +30%에서 내려온다. 기전이 아니라 잡음의 모양이다.

여기서는 **모든 익절선이 기준보다 나쁘다**. 그리고 단조롭다 — 선을 높일수록

되돌림이 애초에 없다는 것이 이 결론의 뿌리다. 5일 보유 전략에서 이긴
매매가 고점 근처에서 끝난다면, 익절이 할 일이 없다. 만약 나중에 보유 기간을
크게 늘리는 전략을 쓰게 되면 그때 다시 재야 한다 — 이 결론은 "익절이
나쁘다"가 아니라 **"보유 5일짜리에서는 할 일이 없다"** 이다.

## 17. 전략을 여러 개 걸기 — AND / OR

지금까지 실거래에 걸 수 있는 전략은 **하나**였다. 전략마다 잘 맞는 장이
다른데, 하나만 고르면 그 성격을 통째로 받아들이는 수밖에 없다.

`CombinedStrategy`가 N개를 묶는다. **개수 제한은 없다.**

- **OR (하나라도)** — 어느 하나가 사라고 하면 산다. 기회가 늘고 신호가 잦아진다.
- **AND (모두)** — 같은 날 같은 종목에 전부 사라고 해야 산다. 기회가 크게
  줄고 조건이 까다로워진다.

### 파는 쪽은 언제나 OR다 — 설정으로 두지 않았다

AND로 팔면 **하나라도 반대하면 못 파는** 구조가 된다. 나머지가 전부 "팔라"고
해도 한 전략이 침묵하는 동안 계속 들고 있게 된다. 손실을 키우는 방향의
실수는 되돌리기 어렵다. **살 때는 까다롭게, 팔 때는 관대하게.**

### AND의 점수는 가장 약한 근거를 쓴다

자리가 모자라면 엔진이 점수 순으로 줄을 세운다(§ 진입 정렬). AND로 묶은
신호의 점수를 **최댓값**으로 잡으면, 한 전략에서 90점이지만 다른 전략에서
간신히 통과한 종목이 앞줄에 선다. 그래서 AND는 **최솟값**, OR은 **최댓값**을
쓴다 — 각각 "가장 약한 근거"와 "가장 강한 근거"다.

### 보유 기간은 가장 짧은 것을 따른다

한 전략이 "5일 지나면 무조건 판다"고 정해 뒀는데 다른 전략 때문에 더 들고
있으면, 그 전략은 **자기가 검증된 조건 밖에서** 도는 것이 된다.

### 아직 안 한 것

**묶음의 성과는 검증하지 않았다.** 지금까지의 백테스트는 전부 전략 하나
기준이다. AND로 묶으면 신호가 며칠씩 안 뜨는 것이 정상인데, 그게 좋은
것인지는 재 봐야 안다. 조합을 고르기 전에 `run_experiment.py`로 그 조합을
먼저 돌려 보는 것이 순서다.

## 18. 대시보드 설정 저장이 터지던 이유

자동매매 스위치를 끄면 `sqlalchemy.exc.OperationalError`가 났다.

대시보드는 30초마다 구글드라이브에서 `muwon.db`를 다시 받아 `os.replace`로
갈아 끼운다. 파일 **이름**은 같지만 **실체**가 바뀐다. 그런데 SQLAlchemy가
연결을 풀에 담아 두면, 그 연결은 이미 사라진 옛 파일을 계속 붙들고 있다.
읽기는 옛 내용을 조용히 돌려주고(그래서 화면은 멀쩡해 보였다), 쓰기는 커밋
순간 터진다.

SQLite 파일 DB는 `NullPool`로 바꿨다 — 세션마다 경로로 새로 열어 항상 "지금
그 자리에 있는 파일"을 본다. 사람이 스위치를 누르는 빈도에서 연결을 다시
여는 비용은 문제가 되지 않는다.

**오류를 잡아서 화면에 띄우는 것도 함께 넣었다.** 안 잡으면 Streamlit이
"error message is redacted"라고만 하고 진짜 원인을 감춘다 — 이번에 무엇이
문제인지 화면만으로는 알아낼 방법이 없었다.

## 19. 전략 22개 줄 세우기 (60종목 · 2021~2025)

묶음을 논하기 전에 기준선이 필요했다. 등록된 22개 전부를 같은 데이터·같은
예열 조건으로 돌렸다.

**5년 내내 플러스인 전략은 셋뿐이다.**

| 전략 | 평균 | 최악 | Sharpe | MDD | PF | 거래 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| **volume_surge_5d** | **+50.5** | **+13.0** | **1.70** | **−14.0** | 1.36 | 1259 |
| ma_rsi_fast5_20 | +24.3 | +12.8 | 1.26 | −28.5 | 1.27 | 1150 |

나머지 19개는 어느 해엔가 마이너스였고, 대부분 2022년이었다. 평균만 높은

## 20. 셋을 묶어 봤다 — 기각

§19의 셋을 OR·AND로 묶고, 각각 혼자 돌린 것과 같은 표에 뒀다.

| 설정 | 평균 | 최악 | Sharpe | MDD | PF | 거래 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| volume_surge_5d 단독 | **+50.5** | +13.0 | **1.70** | −14.0 | 1.36 | 1259 |
| ma_rsi_fast5_20 단독 | +24.3 | +12.8 | 1.26 | −28.5 | 1.27 | 1150 |
| volume_surge_3d 단독 | +29.9 | +6.6 | 1.59 | −15.6 | 1.38 | 887 |
| **[OR] 셋** | +34.1 | **+17.5** | 1.37 | −29.7 | 1.20 | 2433 |
| **[AND] 셋** | +8.1 | −0.3 | 1.17 | **−6.7** | **2.04** | 160 |

### OR — 최악 구간만 좋아지고 나머지는 다 나빠졌다

최악이 +13.0 → **+17.5**로 올라간 것은 진짜다. 그러나 평균이 +50.5 →
+34.1로 깎이고 **MDD가 −14.0 → −29.7로 두 배 나빠졌다**. 거래는 2,433건 —
세 전략 거래 수의 합이다. 회전율이 그만큼 오르면 슬리피지가 그대로 붙는다
(§13에서 잰 바로는 0.10%만 잡아도 volume_surge_5d 평균이 +50.5 → +36.2).

즉 OR은 **약한 전략을 섞어 강한 전략을 희석한 것**에 가깝다.

### AND — 질은 좋아졌는데 양이 사라졌다

PF 2.04, MDD −6.7%는 표에서 가장 좋은 값이다. 셋이 동시에 동의한 자리만
샀으니 당연히 정확도가 오른다. 그런데 5년에 **160거래**뿐이고, 평균이
+8.1%로 주저앉았다. 그리고 **5년 내내 플러스가 깨졌다**(2021 −0.3%).

"틀리지 않지만 벌지도 않는다"는 상태다.

### 이 실험의 한계 — 고른 셋이 애초에 안 다양했다

`volume_surge_5d`와 `volume_surge_3d`는 **같은 전략의 파라미터 변형**이다
(거래량 급증 2배/5일 vs 3배/3일). 성적 순으로 고르다 보니 사실상 두 종류를
묶은 셈이 됐다. 분산 효과를 기대할 수 있는 조합이 아니었다.

그래서 이 결과는 **"묶기가 나쁘다"가 아니라 "비슷한 것끼리 묶으면 소용
없다"** 로 읽는 것이 맞다. 다음에는 계열이 다른 조합으로 다시 재야 한다 —
다만 계열이 다른 전략들은 하나같이 최악 구간이 −20% 아래라, 그것들을
섞어서 최악을 끌어올릴 수 있는지가 진짜 질문이다.

## 21. 계열이 다른 조합 넷 — 전부 기각

§20에서 "비슷한 것끼리 묶어서 소용없었던 것"이라고 봤으니, 계열을 다르게
섞어 다시 쟀다.

| 조합 | 평균 | 최악 | 낙폭 | 거래 |
| --- | ---: | ---: | ---: | ---: |
| volume_surge_5d **단독** (기준) | **+50.5** | **+13.0** | **−14.0** | 1259 |
| [OR] 급증5일+EMA교차+볼린저복귀 | +23.7 | −16.4 | −25.6 | 1912 |
| [OR] 급증5일+MA5/20+스토캐스틱 | +37.5 | −3.7 | −24.3 | 2393 |
| [OR] 급증5일+MACD+RSI반등 | +21.9 | −24.2 | −30.7 | 2313 |
| [OR] MA5/20+EMA교차+볼린저복귀 | +15.4 | −11.9 | −21.0 | 1788 |
| [AND] 위 조합들 | ≈0 | ≈0 | ≈0 | **1, 1, 26, 1** |

### 두 가지가 분명해졌다

**OR은 언제나 희석이다.** 다섯 조합(§20 포함) 전부 평균이 최고 구성원보다
낮았다. 계열을 다르게 해도 마찬가지였고, 오히려 §20의 유사 조합에서
좋아졌던 최악 구간마저 여기서는 나빠졌다(+13.0 → −3.7~−24.2). 거래 수는
언제나 구성원의 합이라 회전율 비용이 그대로 얹힌다.

**AND는 계열이 다르면 작동하지 않는다.** 넷 중 셋이 5년에 **거래 1건**이다.
성격이 다른 전략 셋이 같은 날 같은 종목에 동시에 신호를 낼 일이 사실상
없기 때문이다. AND가 뜻이 있으려면 신호가 겹칠 여지가 있어야 하고, 그건
곧 **비슷한 전략끼리여야 한다**는 뜻이다. 그런데 비슷한 것끼리 묶으면
(§20) 이번엔 분산 효과가 없다.

즉 AND는 구조적으로 갇혀 있다 — 겹치면 분산이 없고, 안 겹치면 안 산다.

**1위 전략을 뺀 조합**(MA5/20+EMA교차+볼린저복귀)도 평균 +15.4%로 세
구성원 중 어느 것보다도 낮았다. "좋은 것 하나가 끌고 가서 그렇다"는 설명도
성립하지 않는다.

### 남는 것

지금 데이터에서 묶기는 **1위 전략을 혼자 쓰는 것보다 나은 구성을 하나도
찾지 못했다.** 기능은 남겨 둔다 — 전략 목록이 바뀌면 답도 바뀔 수 있고,
재는 도구(`combo` 모드)가 이제 있다.

## 22. 전략 성적표 — 흩어진 결과를 한 장으로

실험 결과가 세 군데에 흩어져 있었다. 숫자는 Actions 로그(만료된다)와
아티팩트에, 판단은 이 설계안에, 가설의 채택·기각은 구글 시트에. "이 전략
써도 되나"를 물으면 세 곳을 다 뒤져야 했고, 코드를 안 보는 사람은 애초에
접근할 수가 없었다.

`docs/전략평가.json` + 대시보드 **전략 → 전략 성적표**.

### 판정은 사람이 매기지 않는다

항목마다 손으로 매기면 "이건 평균이 높으니까 봐주자"가 한 번 들어가고,
그러면 표 전체를 믿을 수 없게 된다. `판정하기(최악, 거래)`가 정한다.

- 5년에 **50건 미만** 거래 → **보류** (판단할 표본이 없음)
- 가장 나빴던 해가 **0% 이상** → **쓸만함**
- **−20%보다 위** → **조건부**
- **−20% 이하** → **안씀**

**평균이 아니라 최악의 해로 매긴다.** 평균이 아무리 높아도 한 해에 30%
잃으면 대부분 중간에 그만두고, 그러면 평균은 받아 보지도 못한다. 이 규칙
때문에 EMA교차(평균 +43.4%)가 '안씀'이 된다 — 표를 보는 사람이 동의하지
않을 수 있으므로 규칙을 화면에 그대로 띄운다.

결과: **쓸만함 3 · 조건부 7 · 안씀 11 · 보류 1**.

### 다시 계산하지 않는다 — 그래서 위험한 것

실험은 몇 분씩 걸려 화면을 열 때마다 돌릴 수 없다. 그래서 이 표는 **기록**
이고, 가장 위험한 실패 방식은 **옛 숫자를 최신인 척 보여 주는 것**이다.

- 항목마다 어느 실행에서 나왔는지(`실행`, `커밋`)를 적는다
- 측정일이 30일을 넘으면 화면이 스스로 경고한다
- 생성 스크립트가 저장된 파일을 그대로 재현하는지 테스트가 확인한다
  (손으로 고친 채 잊으면 화면과 스크립트가 서로 다른 말을 한다)

## 23. 진입 시점 — 가설이 반대 방향으로 틀렸다

§16에서 **손실 매매의 28%가 '산 날이 곧 고점'** 이라는 것을 확인했다.
백테스트는 신호가 난 **그날 종가**에 산다(`BacktestEngine`의 진입 경로).
지금 전략은 "거래량 2배 급증 + 그날 2% 이상 상승"에서 신호를 내므로, 산
날이 고점이라는 건 곧 **급등 꼭지를 샀다**는 뜻이다.

그래서 이렇게 봤다 — *많이 오른 날일수록 이미 힘이 빠져 나쁠 것이다.
상한을 두면(2% 이상 오르되 8%는 넘지 않은 날) 나아진다.*

완결 매매 **1,259건**을 진입일 특성으로 나눠 봤다. 결과를 미리 나누지
않는다 — 이긴 매매만 골라 특징을 찾으면 어떤 숫자든 그럴듯한 이야기가
나온다.

### 그날 얼마나 올랐나

| 구간 | 건수 | 승률 | 평균 손익 | 중앙 손익 |
| --- | ---: | ---: | ---: | ---: |
| 2~4% | 267 | **43.8%** | +0.96% | **−0.67%** |
| 4~6% | 331 | 47.1% | +0.72% | −0.18% |
| 6~8% | 238 | 49.6% | +1.63% | +0.00% |
| 8~12% | 233 | 48.1% | +0.87% | −0.10% |
| **12% 이상** | 190 | **50.5%** | **+2.85%** | **+0.29%** |

### 그날 거래량이 평소의 몇 배였나

| 구간 | 건수 | 승률 | 평균 손익 | 중앙 손익 |
| --- | ---: | ---: | ---: | ---: |
| 2~3배 | 635 | 48.2% | +1.13% | −0.19% |
| 3~5배 | 394 | **44.7%** | +0.84% | **−0.71%** |
| 5~10배 | 152 | 48.7% | +2.80% | −0.15% |
| **10배 이상** | 72 | **52.8%** | +1.48% | **+1.08%** |

### 방향이 반대였다

가장 조심스러운 진입(2~4% 상승)이 **가장 나빴고**, 가장 과격한 진입(12%
이상, 거래량 10배 이상)이 **가장 좋았다**. 상한을 두면 가장 좋은 구간을
잘라 내는 셈이다.

**즉 "산 날이 고점" 28%는 결함이 아니다.** 이 전략은 원래 대부분 조금씩
잃고 가끔 크게 버는 방식이다 — 중앙 손익이 거의 모든 구간에서 마이너스인데
평균은 플러스인 것이 그 증거다. 익절이 도움이 안 됐던 이유(§16)와 같은
구조다.

### 작은 표본으로 판단할 뻔했다

이 실험을 18종목 1년(72건)으로 먼저 돌렸을 때는 **거래량 10배 이상 구간의
승률이 0%** 였다. 그걸 보고 "과열은 피하자"로 갔으면 정반대로 갔을 것이다.
그 칸은 **2건**이었다.

60종목 5년(1,259건)에서 같은 칸은 72건에 승률 52.8%로 **가장 좋은 구간**
이다. 구간을 나눠 보는 분석은 칸이 잘게 쪼개지므로, 각 칸의 건수를 먼저
보는 습관이 필요하다.

### 남은 것

상한은 기각. **하한을 올리는 쪽**(예: 2% → 6%)은 아직 안 재봤다. 위 표는
2~4% 구간이 가장 나쁘다고 말하므로 그쪽은 해 볼 값이 있다 — 다만 그러면
거래 수가 줄어 표본이 얇아진다.

## 24. 실시간 구조로 바꿔야 하나

"장 초반·후반에만 매매하는 구조 말고, 장중에 실시간으로 지표를 읽고
판단하는 구조로 바꾸면 안 되나"라는 물음이 나왔다.

### 구조는 이미 있다

`RealtimeTradingEngine`(`execution/realtime_engine.py`)이 이미 있다. 장이
열려 있는 동안 계속 떠서 **분봉이 하나 마감될 때마다** 판단하고, 전략
판정과 리스크 검증 코드는 지금 것을 그대로 재사용한다. 다른 건 "언제
판단하느냐"뿐이다.

다만 KIS 웹소켓 연동은 **실제 접속이 검증된 적이 없다** — 개발 환경에서
KIS 포트가 막혀 있었다(`docs/deploy_vps_realtime.md` 0절).

### 바꾸면 잃는 것이 크다

1. **5년 검증이 전부 무효가 된다.** 22개 전략을 검증한 건 전부 일봉이고,
   분봉 과거 데이터가 없어 같은 방식으로 다시 검증할 방법이 없다.
2. **지표의 뜻이 달라진다.** "20일 이동평균"을 1분봉에 그대로 쓰면 **20분
   이동평균**이 된다. 이름만 같은 다른 것이다. 즉 구조 변경이 아니라
   **검증한 적 없는 새 전략으로 갈아타는 것**이다.
3. **회전율이 폭증한다.** 슬리피지가 이미 가장 큰 미지수인데(§13, 실측
   표본 0건) 체결 횟수가 몇 배가 된다.
4. GitHub Actions는 상시 연결을 못 하므로 VPS가 필요하다.

### 그래서 손절만 옮겨 봤다 — 그것도 기각

판단을 옮기면 검증이 무효가 되지만 **손절만** 장중으로 옮기는 것은 전략을
안 건드린다. 그 값을 지금 데이터로 잴 수 있다 — 일봉의 **저가**가 손절선을
밑돌았다면 장중 스톱은 그날 발동했을 것이다.

| | 지금 (종가 손절) | 장중 손절 | 차이 |
| --- | ---: | ---: | ---: |
| 매매당 평균 | **+1.29%** | +1.19% | **−0.10%p** |

1,259건 중 **492건(39.1%)** 이 장중 스톱에 걸렸을 것이다. 그런데:

- 좋아진 매매 **349건** (평균 **+2.07%p**)
- 나빠진 매매 **140건** (평균 **−6.10%p**)

**좋아지는 건 자주 조금씩, 나빠지는 건 드물게 크게.** 순합이 마이너스다.

나빠지는 이유는 장중에 잠깐 손절선을 스쳤다가 회복해 마감하는 매매를 그
자리에서 팔아 버리기 때문이다. ATR 손절·트레일링 스톱을 껐을 때(§초기
검증)와 **같은 패턴**이다 — 이 전략은 잡음에 손절당하는 데 특히 약하다.

그리고 이 계산은 **낙관적**이다. 손절선에 정확히 팔렸다고 봤는데, 실제
스톱 주문은 손절선을 건드리면 시장가로 나가 그보다 아래에서 체결된다.
즉 **실제로는 −0.10%p보다 나쁘다.**

### 결론

실시간으로 옮길 이유가 하나 사라졌다. 남은 이유는 "분 단위 신호가 일 단위
신호보다 낫다"는 가정뿐인데, 그건 검증할 데이터가 없다.

**바꾸려면 순서가 있다.** ① 분봉 과거 데이터를 확보하고 ② 그걸로 분봉
전략을 처음부터 검증하고 ③ 웹소켓 연결을 실제로 확인한 뒤다. 지금 상태에서
옮기면 검증된 것을 버리고 검증 안 된 것으로 가는 셈이다.
