# 전략 엔진 고도화 — 현 구조 분석 및 마이그레이션 설계안

인수인계서(Ensemble Score 기반 모듈형 전략 엔진)를 현 코드베이스에 적용하기 위한
분석·설계 문서. **구현 전에 합의할 내용**을 정리한 것이며, 아직 코드는 바꾸지 않았다.

---

## 1. 현 구조 분석

### 1.1 전체 흐름

```
유니버스(시총 상위 18~60)          settings(DB, 암호화·이력)
        │                                  │
        ▼                                  ▼
  KIS/Yahoo 일봉 ──▶ Strategy ──▶ RiskManager ──▶ OrderExecutor ──▶ 알림/DB
                   (종목 1개씩)   (거부만 함)      (시장가 전량)
```

- `TradingEngine`(실거래)과 `BacktestEngine`(백테스트)이 **같은 순서**로 짜여 있다.
  이건 이미 잘 되어 있는 부분이고, 앞으로도 유지해야 한다.
- 전략 21종은 `registry.py`에 등록되고, 활성 전략 키 하나를 DB 설정으로 고른다.
- 리스크 정책·인증정보·텔레그램은 전부 DB(`app_settings`)에 있고 변경 이력이
  자동으로 남는다. 대시보드에서 재시작 없이 바꿀 수 있다.

### 1.2 결정적 제약 — `Strategy` 인터페이스가 종목 하나만 본다

```python
class Strategy(ABC):
    def generate_signals(self, symbol: str, price_history: pd.DataFrame) -> list[Signal]
```

이 시그니처에는 **다른 종목도, 지수도, 날짜별 순위도 들어올 수 없다.** 따라서
인수인계서의 핵심 Factor 중 두 개가 지금 구조에서는 원리적으로 구현 불가능하다.

| Factor | 필요한 것 | 현 인터페이스로 가능? |
|---|---|---|
| Relative Strength | 같은 날 전 종목의 수익률 분포(횡단면 순위) | ❌ |
| Market Regime | 지수 가격·이동평균, 유니버스 전체의 Breadth | ❌ |
| Trend / Momentum / Pullback / Breakout / Volume / Volatility | 해당 종목 시계열만 | ✅ |

**→ 인터페이스 변경이 이 작업의 최우선 선결 과제다.** 이걸 먼저 정리하지 않으면
RS·Regime을 넣으려다 전략 코드 곳곳에 전역 상태를 주입하는 형태가 되어, 문서가
경계하는 "복잡한 조건문을 계속 덧붙이는" 구조로 간다.

### 1.3 발견된 실제 결함 — 전략이 포트폴리오 상태를 들고 있다

`VolumeSurgeStrategy`(현재 활성 전략 `volume_surge_5d`)는 `generate_signals` 안에서
`entry_index` 변수로 "지금 보유 중"을 스스로 기억한다.

실제로 돌려서 확인한 결과:

```
급등일 2번(3일 간격)을 준 데이터 → 매수 신호는 1번만 발생
  2025-01-22 buy   거래량 2배 급증 + 10.0% 상승
  2025-01-27 sell  보유 5일 경과 청산
```

문제는 이 "보유 중"이 **엔진의 실제 보유와 아무 관계가 없다**는 점이다.

- 리스크 매니저가 매수를 거부했거나(동시보유 8종목 초과, 일일 손실 한도),
  현금이 부족해 엔진이 안 샀어도 → 전략은 샀다고 믿고 이후 신호를 막는다.
- 며칠 뒤 내는 매도 신호는 있지도 않은 포지션을 향한 것이라 엔진이 무시한다.

즉 **자리가 없어서 한 번 못 산 종목은, 그 뒤 며칠간 기회가 와도 신호 자체가
안 나온다.** 종목 수를 60개로 늘려 자리 경쟁이 생기면 이 결함의 영향이 커진다.

인수인계서 39항 "전략 로직과 주문 로직을 섞지 않는다"에 정확히 해당한다.
보유 여부 판단은 엔진(포트폴리오)이 갖고, 전략은 "지금 이 종목이 매력적인가"만
답해야 한다.

## 2. 목표 구조와의 차이(Gap)

| 인수인계서 요구 | 현재 | 난이도 |
|---|---|---|
| Factor별 Score | 조건식 True/False | 중 |
| Weight / Enabled / 자동 재정규화 | 없음 | 하 |
| Threshold를 Config에서 | RiskPolicy만 DB, 전략 파라미터는 코드 | 중 |
| Market Regime 상위 Layer | 없음 | **상** (지수·Breadth 데이터) |
| Relative Strength | 없음 | **상** (인터페이스 변경) |
| ATR Stop / Trailing / Take Profit | 고정 % 손절만 | 중 |
| Risk 기반 Position Sizing | 고정 비중 | 중 |
| 섹터 노출 한도 | 섹터 데이터 없음 | **불가(현재)** |
| Fundamental Factor | 데이터 소스 없음 | 보류 |
| 수급(외국인·기관) Factor | 데이터 소스 미확인 | 보류 |
| CAGR/Sharpe/Sortino/PF/Expectancy | 수익률·MDD·승률·거래수만 | 하 |
| Factor Contribution 분석 | 없음 | 하 (Enabled 토글이 생기면 자동) |
| 판단 근거 로그(Explainability) | 사유 문자열 1줄 | 하 |
| Slippage | 미반영 (수수료·세금만) | 하 |
| Look-ahead 방지 | ✅ 이미 처리 | — |
| Walk Forward | ✅ `robustness.py`로 구간별 검증 중 | — |

### 2.1 데이터로 막히는 것 — 솔직히 적는다

- **Fundamental / 수급**: 지금 쓰는 데이터 소스(KIS 일봉, Yahoo)에 없다. KIS에
  투자자별 매매동향 API가 있으나 모의투자 지원 여부를 확인하지 않았다.
  인터페이스만 열어 두고 Phase 7로 미루는 게 맞다.
- **섹터**: 종목별 업종 코드를 안 받아오고 있다. `max_sector_exposure`는
  업종 데이터를 먼저 확보해야 한다.
- **유니버스 60종목 상한**: KIS 순위 API가 시장당 30개까지만 준다(직접 확인).
  RS 백분위를 60개 안에서 매기면 해상도가 거칠다. 늘리려면 연속조회 구현 필요.
- **생존 편향(Survivorship Bias)**: 지금 유니버스는 **오늘 시점** 시총 상위로
  뽑는데, 그걸로 과거를 백테스트하고 있다. 즉 인수인계서 26항이 경계하는
  생존 편향이 **이미 기존 검증 결과에 들어 있다.** 과거 시점의 구성종목을
  KIS에서 받을 방법이 없어 당장 해결이 어렵다 — 최소한 결과에 명시해야 한다.

## 3. 목표 구조 매핑

### 3.1 새 인터페이스 — 유니버스 전체를 보는 전략

기존 `Strategy`를 **없애지 않고** 상위 개념을 추가한다.

```python
@dataclass(frozen=True)
class MarketContext:
    """어느 하루의 판단에 필요한 모든 것. 미래 데이터는 들어가지 않는다."""
    as_of: date
    histories: dict[str, pd.DataFrame]   # 종목별, as_of까지만 잘라서
    index_history: pd.DataFrame | None   # 지수(시장 국면용)
    held: set[str]                       # 지금 보유 중인 종목 — 전략은 읽기만


@dataclass(frozen=True)
class Evaluation:
    """한 종목에 대한 평가 결과 — 점수와 '왜'가 함께 다닌다."""
    symbol: str
    total_score: float
    factor_scores: dict[str, float]
    decision: str          # NO_TRADE / WATCH / BUY / STRONG_BUY
    reasons: list[str]


class PortfolioStrategy(ABC):
    def evaluate(self, ctx: MarketContext) -> list[Evaluation]: ...
```

기존 21종은 어댑터로 감싸 같은 경로에 태운다.

```python
class SingleSymbolAdapter(PortfolioStrategy):
    """기존 Strategy 하나를 유니버스 전체 평가로 변환. 매수 신호=100점,
    없으면 0점. 기존 전략을 대조군으로 계속 쓰기 위한 다리."""
```

이렇게 하면 **대시보드·전략 리뷰·다기간 검증·리포트가 전부 그대로 동작**한다.
새 엔진은 registry에 전략 하나(`factor_score_v1`)로 추가되어, 기존 21종과 같은
자리에서 비교된다. 이게 이 프로젝트에서 가장 위험이 적은 이식 경로다.

### 3.2 디렉터리

인수인계서 32항 구조를 현 패키지에 맞춰 배치한다.

```
src/muwon/
  factors/            (신규)
    base.py           Factor 인터페이스 + 정규화 도우미
    trend.py  momentum.py  pullback.py  breakout.py
    relative_strength.py   volume.py    volatility.py
    (fundamental.py  flow.py — Phase 7)
  market/             (신규)
    regime.py         국면 판정 + 국면별 파라미터
  scoring/            (신규)
    engine.py         Weight 적용·재정규화·임계값 판정
    config.py         FactorConfig / StrategyConfig 스키마
  risk/               (기존 확장)
    manager.py        기존 유지
    sizing.py         (신규) ATR 기반 수량 계산
    exits.py          (신규) ATR 손절/트레일링/이익실현
  backtest/
    metrics.py        (신규) CAGR·Sharpe·Sortino·PF·Expectancy
```

`factors/new_factor.py`를 추가하고 config에 한 줄 넣으면 끝나는 구조를 목표로 한다.
Score Engine은 Factor 목록을 순회할 뿐 개별 Factor를 알지 못한다.

### 3.3 Factor 공통 인터페이스

```python
class Factor(ABC):
    key: str                       # config에서 참조할 이름

    def score(self, symbol: str, ctx: MarketContext) -> FactorResult:
        """0~100으로 정규화된 점수와 근거 문장을 돌려준다.
        데이터가 모자라면 None을 돌려 '평가 불가'로 처리하고,
        그 Factor의 가중치는 재정규화에서 빠진다."""
```

> **정규화 규칙을 처음부터 못 박아 둔다: 모든 Factor는 0~100.** 지금 엔진에 넣은
> `Signal.score`는 전략마다 척도가 다른데(거래량 배수, 돌파 폭 %), 그건 "한 번에
> 한 전략만 돈다"는 전제 위에서만 성립한다. 여러 Factor를 더하는 순간 척도가
> 통일돼 있지 않으면 가중치가 아무 의미도 갖지 못한다.

### 3.4 설정 스키마

```json
{
  "buy_threshold": 75,
  "strong_buy_threshold": 85,
  "factors": {
    "market_regime":     {"enabled": true,  "weight": 15, "params": {}},
    "trend":             {"enabled": true,  "weight": 15, "params": {"mas": [20,60,120,200]}},
    "momentum":          {"enabled": true,  "weight": 20, "params": {"periods": [5,20,60,120]}},
    "relative_strength": {"enabled": true,  "weight": 20, "params": {"benchmark": "^KS11"}},
    "pullback":          {"enabled": true,  "weight": 20, "params": {"rsi_period": 5, "rsi_max": 35}},
    "volume":            {"enabled": true,  "weight": 10, "params": {"ma_window": 20}},
    "breakout":          {"enabled": false, "weight": 10, "params": {"period": 55}},
    "fundamental":       {"enabled": false, "weight": 10, "params": {}},
    "flow":              {"enabled": false, "weight": 10, "params": {}}
  },
  "exits": {
    "atr_stop":      {"enabled": true, "multiple": 2.0},
    "trailing_stop": {"enabled": true, "multiple": 3.0},
    "trend_exit":    {"enabled": true},
    "score_exit":    {"enabled": true, "threshold": 50},
    "take_profit":   {"enabled": false, "steps": [[2, 0.33], [4, 0.33]]}
  },
  "sizing": {"risk_per_trade_pct": 0.5, "max_position_pct": 15, "max_exposure_pct": 80}
}
```

- `enabled=false`인 Factor는 합계에서 빠지고 **나머지 가중치를 100 기준으로 자동
  재정규화**한다(인수인계서 5항).
- 데이터가 없어 평가 불가인 Factor도 같은 방식으로 빠진다. 이게 없으면 수급
  데이터가 하루 안 들어온 날 전 종목 점수가 통째로 내려앉는다.

### 3.5 국면별 파라미터 override

```json
{
  "regimes": {
    "STRONG_BULL": {"buy_threshold": 70, "max_exposure_pct": 100},
    "BULL":        {"buy_threshold": 75, "max_exposure_pct": 80},
    "NEUTRAL":     {"buy_threshold": 80, "max_exposure_pct": 50},
    "BEAR":        {"buy_threshold": 90, "max_exposure_pct": 20}
  }
}
```

**Breadth는 우리 유니버스 60종목으로 계산한다.** 별도 데이터 소스가 필요 없고
(이미 60종목 일봉을 다 받아온다), 지수 데이터가 막혀도 국면 판정이 돌아간다.
지수(`^KS11`)는 백테스트에서 Yahoo로 확보 가능하고, 실거래에서는 KIS 업종지수
조회가 필요하다 — **미확인이므로 Breadth 단독으로도 작동하게 설계한다.**

## 4. 단계별 Migration Plan

각 단계는 **기존 21전략이 계속 동작한 채로** 끝나야 한다.

### Phase 1 — 경계 정리 (기능 변화 없음)

1. `MarketContext` / `Evaluation` / `PortfolioStrategy` 정의
2. `SingleSymbolAdapter`로 기존 21종을 새 경로에 태움
3. 두 엔진(실거래/백테스트)이 `PortfolioStrategy`만 호출하도록 변경
4. **`VolumeSurgeStrategy`의 보유 상태를 엔진으로 이관** (§1.3 결함 수정)

> 이 단계의 성공 기준: **21전략의 백테스트 결과가 이전과 100% 동일**할 것.
> (단 `volume_surge_5d`는 결함 수정으로 결과가 달라진다 — 그 차이를 별도 보고)

### Phase 2 — Config 골격

5. `StrategyConfig` 스키마 + DB 저장(JSON) + 기본값
6. Weight 재정규화 로직 + 임계값 판정
7. 대시보드에 Factor 목록 표시(읽기 전용)

### Phase 3 — 핵심 Factor 6종

8. `trend` `momentum` `pullback` `volume` (종목 단위)
9. `relative_strength` (횡단면 — 새 인터페이스가 있어야 가능)
10. `market_regime` (Breadth 기반, 지수는 선택)
11. `factor_score_v1`을 registry에 등록 → 기존 21종과 나란히 비교

### Phase 4 — Score Engine 완성 + Explainability

12. 판단 근거 JSON 저장(`SignalRow` 확장 또는 신규 테이블)
13. 텔레그램·대시보드에 "왜 샀는지" 표시

### Phase 5 — Risk Engine 분리

14. ATR 손절 / 트레일링 / 시간 청산 / Score 청산
15. Risk 기반 Position Sizing (`max_position_weight`의 이중 역할 해소)

### Phase 6 — 백테스트 지표 고도화

18. Slippage 반영

### Phase 7 — 확장 Factor

### Phase 8 — 대시보드 설정 UI

## 6. 확인이 필요한 의사결정

| # | 질문 | 선택지 | 권장 |
|---|---|---|---|
| D1 | 전략 설정을 어디에 둘까 | ① DB(JSON) ② 저장소 YAML 파일 | **①** — 기존 설정이 전부 DB에 있고 대시보드에서 재시작 없이 바꾸며 변경 이력이 자동으로 남는다. YAML은 값 하나 바꿀 때마다 git push가 필요해 이 시스템의 운영 방식과 어긋난다 |
| D2 | 기존 21전략 처리 | ① 어댑터로 유지 ② 폐기하고 Factor로 흡수 | **①** — 다기간 검증 baseline이자 대조군이다. 새 엔진이 이들보다 나은지 비교할 기준이 사라지면 안 된다 |
| D3 | Position Sizing 전환 시점 | ① Phase 5까지 기존 고정비중 유지 ② Phase 1에 함께 | **①** — 사이징까지 같이 바꾸면 성과 변화가 Factor 때문인지 사이징 때문인지 구분이 안 된다 |
| D4 | Market Regime 데이터 | ① Breadth(우리 60종목) 우선 ② 지수 필수 | **①** — 지수 조회가 막혀도 돌아가야 한다 |
| D5 | 생존 편향 | ① 명시하고 진행 ② 과거 구성종목 확보 후 진행 | **①** — KIS에서 과거 시점 구성종목을 받을 방법이 없다. 결과 해석 시 감안하는 편이 현실적 |
| D6 | 유니버스 60종목 상한 | ① 유지 ② 연속조회로 100+ | 나중 — RS 해상도는 60에서도 실험 가능 |

## 7. 이 설계에서 지키는 원칙

인수인계서 39항을 이 프로젝트 문맥으로 옮기면 다음과 같다.

1. Factor는 0~100으로 정규화한다 — 안 그러면 Weight가 의미를 잃는다
2. Factor 추가 시 Score Engine을 고치지 않는다
3. 전략은 포트폴리오 상태를 갖지 않는다 (§1.3 결함이 그 반례)
4. 리스크와 사이징을 전략에서 분리한다 (`max_position_weight` 이중 역할 해소)
5. 모든 판단은 근거를 남긴다 — 점수만으로는 디버깅이 불가능하다
6. 각 Phase는 기존 기능을 깨지 않고 끝난다
7. 새 전략이 기존 21종보다 낫다는 것은 **백테스트로 확인한 뒤** 말한다
